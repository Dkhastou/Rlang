# Design Plan

## First Version

### Workflow

1. Create a language. There is a way to 'activate' the language so that all lang commands refer to the language automatically. It will show a '(<'language-name'>)' next to the standard console prompt. the command will be `langsmith activate <'language-name'>`. Now all commands read the current language without it needing to be prompted explicitly. There is also a corresponding `deactivate` command. 
1.5 (not a priority yet) The user can generate a symbol space, which is an abstract space defined via information theory that defines which kinds of symbols are allowed. In our current working version, the symbol space is a 3x3 grid with allowed connections between points on the grid, and specific marks that can be used. We can use information theory to define 
2. Generate symbols as part of the language. Symbols are a simple .svg file which chafa can easily display on the terminal. Or, more precisely, symbols can be a .svg file bundled with some other data so that they easily display on the terminal. For example, they will display .svg files but with the background color set to match the terminal background color and foreground color set to match the terminal foreground color
3. Symbols are nodes of a graph, relations between symbols are edges of the graph. I can use the standard RDF protocol which already exists. Combine this with OWL which sits on top of RDF and provides typed structure 
4. A language is a collection is a symbol space (eventually), a collection of symbols defined from it that are generated by the user, a semantics, and graph based relations between symbols. 

For actually using the language, there is a live 'editor' with hotkeys, which is a way for the user to type out the language. It will function similar to a terminal. A list of relevant commands will be displayed upon opening up the editor. The editor allows the following:

1. The user can list all the symbols they have using the 'l' command and select one of them using a menu selector that way. 
2. Or, after listing all the symbols, they can assign keyboard keys to each symbol. For now, we will only allow the user to assign symbols to keys 1,2,3,...,0 to avoid hot-key conflicts
3. These hotkey mappings get saved inside a file so they can be edited directly later. The file encodes the associated current working language too
4. The user can then type the language out inside the editor. Becuase the hotkey prefereneces get saved in the file, if they close the editor and open it up again, all of their assignments are saved. 
5. After the user types something in their language, they can save the output as another .svg file. (This can be converted into a regular image file later)

Down the road, it is probably better to save outputs as binary so that the information is stored exactly as it needs to be. Then there can be a converter associated with each language which takes the binary and converts it into the corresponding language. 

### Other ideas

1. So far, all of this works well for formal languages, but the main distinction between formal languages and native languages is that in native languages, meaning drifts as the language gets used. One way to expand communication would be to implement the use of feedback loops or something, which make it so that as the user uses the language, the semantics of the words drift. 
2. Eventually, we can move to meaning being stored in sounds as opposed to just images, or at least have some kind of mapping between images and sound

Icons make learning languages easier. There is probably some way to move between icons and symbols, for example an emoji next to some abstract symbol or something.
